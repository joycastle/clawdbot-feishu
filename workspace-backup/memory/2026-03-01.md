## 教训：代码链路分析要完整

**场景**：分析 BF 项目的"拯救球加球函数"逻辑时，给出了不准确的结论。

**问题**：
1. 只看了 `addRescueBall` 函数本身，没有追溯调用方
2. 对 `@ScopeSettlement` 装饰器理解有偏差，以为会自动触发逻辑
3. 有工具（find-refs、call-graph）但没用起来
4. 急于回答而不是先调查清楚

**正确做法**：
1. 遇到"某函数做了什么"的问题，先用工具找调用方
2. 画出完整调用链：上游 → 目标函数 → 下游
3. 追踪数据流向（数据从哪来、到哪去、有没有进背包等）
4. 再下结论

## 新工具：调用图查询 (Graph API)

**背景**：用户建议用图数据库存调用关系，比文本搜索更直接。

**实现**：
- 用 ts-morph 提取 14,843 节点 + 57,216 条边
- 存入 SQLite (`call-graph.db`)
- 集成到 code-index API (port 18801)

**新端点**：
```bash
# 谁调用了这个函数（最常用）
curl "http://127.0.0.1:18801/graph/callers?name=addRescueBall"

# 两点间的调用路径（追链路）
curl "http://127.0.0.1:18801/graph/path?from=claimRoundAward&to=addRescueBall"
# 返回: RoundService.claimRoundAward -> updateActiveCampaignTotalTicketCost -> CampaignRescueRushService.addRescueBall

# 这个函数调用了谁
curl "http://127.0.0.1:18801/graph/callees?name=xxx"

# 函数信息
curl "http://127.0.0.1:18801/graph/info?name=xxx"
```

**关键文件**：
- 提取脚本：`~/work/bf/nakama-ts/tools/extract-call-graph.ts`
- 查询工具：`~/work/bf/nakama-ts/tools/query-graph.ts`
- API 服务：`~/.clawdbot/extensions/feishu/src/services/code-index-api.ts`
- 数据库：`~/.clawdbot/extensions/feishu/data/code-index/call-graph.db`

**开发过程中的坑**：
1. 递归 CTE 的 LIMIT 不能放在 UNION ALL 里面 → 改用 BFS 手动实现
2. better-sqlite3 查询崩溃 → 加 try-catch
3. 端口冲突 → 杀进程重启
